# Records Agent Tools Eval Results v0.8.4

Hardening release: every item below was shipped with an explicit goal and a
verification step, including one documented negative result.

## 1. Claude Code end-to-end test (`scripts/claude-e2e.mjs`, `npm run test:claude`)

- **Goal:** close the platform asymmetry where Codex had a staged
  install-and-invocation e2e but Claude Code only had manifest validation —
  v0.8.2 changed the reviewer agent's tool surface with zero runtime
  verification.
- **Staged tier (always on, wired into `npm run check`):** asserts the
  reviewer allow-list is exactly the audited five tools, no `disallowedTools`
  regression, the declared `fhir-validation` skill and every reference file it
  names resolve on disk, all fixture-relevant commands point at
  `${CLAUDE_PLUGIN_ROOT}`, and the pinned CLI strictly validates a staged
  copy. Verified locally: passes.
- **Live tier (`RECORDS_CLAUDE_E2E_LIVE=1`):** runs the pinned CLI headless
  with `--plugin-dir` and `--agent fhir-validation-reviewer`, then asserts
  from the stream-json transcript that the agent reads its skill reference, a
  requested Write probe never lands on disk, and every tool actually used is
  inside the allow-list. Verified live on 2026-08-17: all assertions passed.
  This empirically closes the question open since v0.8.2 of whether the
  allow-list strands the declared skill — it does not. (CLI auth note: with
  no global install, authenticate the pinned CLI via `npx claude auth login`.)

## 2. Release-chain automation (`scripts/release.mjs`, tag rule in `release-check.mjs`)

- **Goal:** make the v0.8.2/v0.8.3 failure class impossible — released
  versions on `main` without git tags or GitHub releases, `/releases/latest`
  three weeks stale.
- **Tag rule:** every `eval-results/vX.Y.Z.md` version except the current one
  must have a `vX.Y.Z` git tag. Verified by negative test: the rule flagged
  the two genuinely missing historic tags (v0.2.0, v0.2.1), which were then
  created on their real release commits; the check passes afterwards. v0.7.0
  is exempted with an in-code comment: it never had a release commit (its
  eval file first landed in the v0.8.0 commit), so there is no honest commit
  to tag.
- **`npm run release`:** verifies clean `main`, no pre-existing tag, full
  check suite, then tags and prints the exact push and `gh release create`
  commands. Pushing stays manual. Verified: guards fire correctly on a dirty
  tree and an existing tag.

## 3. Registry re-sync automation (`scripts/registry-sync.mjs`, `npm run registry:sync`)

- **Goal:** replace the manual ClaudeRegistry vendoring procedure performed
  by hand for v0.8.2 and v0.8.3 within ten days.
- **Verification:** a full local run cloned the fork, branched from upstream
  `main`, vendored the plugin byte-identically (`diff -r` empty), updated the
  marketplace entry, and passed the registry's own verifier 7/7 plus registry
  `--ci` mode. Pushing and opening the PR stay manual.

## 4. Bash scoping for the reviewer agent — documented negative result

- **Goal:** move the agent's read-only contract from prompt level toward
  enforcement by scoping Bash to validator commands.
- **Finding:** current Claude Code documentation states the agent `tools:`
  frontmatter does **not** accept permission patterns like `Bash(node:*)` —
  only plain tool names, MCP server patterns, and agent types
  (code.claude.com/docs/en/sub-agents.md). A blocking PreToolUse hook could
  enforce a command allowlist but would violate ClaudeRegistry's hook-safety
  methodology, which requires advisory-only hooks. Decision: allow-list stays
  as audited; the limitation stays documented here and in the v0.8.2 release
  notes. Revisit if agent-level permission rules ship.

## 5. Live prompt evals (`scripts/eval-prompts.mjs`, `npm run eval:prompts`)

- **Goal:** automate the most regression-prone scenarios from `evals.md`,
  previously a fully manual pre-release checklist.
- **Scenarios:** structural gaps named for a pasted invalid Observation
  (#2), FHIR-URL validation surfaces the consent gate and fetches nothing
  (#10), a generic JSON Schema request does not route into Records skills
  (#19), and the bundled fixture resolves without a user-supplied path
  (v0.8.4 quickstart fix). Assertions run against stream-json transcripts,
  including which tools were actually invoked.
- **Verification:** gate behavior verified (skips cleanly without
  `RECORDS_CLAUDE_E2E_LIVE=1`); all four scenarios passed live on
  2026-08-17. Scenario 4 doubles as empirical confirmation that
  `${CLAUDE_PLUGIN_ROOT}` resolves in command bodies, which the docs leave
  ambiguous. Model-behavior assertions are signal-based (findings named,
  consent gate surfaced, no fetch tools, no Records skill invocation), not
  exact-output matches.

## 6. Post-install quickstart fixtures

- **Goal:** bundled fixtures were unreachable after a marketplace install
  because README and command examples used repo-relative paths.
- **Change:** `validate`, `doctor`, and `explain-outcome` commands now tell
  the model that bundled fixtures live under `${CLAUDE_PLUGIN_ROOT}/fixtures/`
  (the variable the same commands already use for their scripts), and both
  READMEs explain the post-install path. Verified structurally by the staged
  e2e and behaviorally by prompt-eval scenario 4, which located the bundled
  fixture and reported its issues without a user-supplied path.
